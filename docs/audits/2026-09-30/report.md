### P1: グループのカレンダー再訪で表示が消える

グループ詳細内のタブを戻しただけで、表示済みの活動データが失われる。2回目の応答を保留すると640kg表示が消え、同日ボタンがdisabledになった。応答を再開すると戻るため、再取得の完了が表示・操作の条件になっている。

[再現画像](images/calendar-revisit-pending.png)。[group-screen.tsx](../../../frontend/src/features/v2/group-screen.tsx) はカレンダーとグラフを条件付きで表示する。[group-history-calendar.tsx](../../../frontend/src/features/v2/group-history-calendar.tsx) の月選択・取得結果と [use-resource.ts](../../../frontend/src/features/training/use-resource.ts) のcacheは部品内にある。グラフにも同じ破棄構造があるが、今回の動的再現はカレンダーのみ。

採用した修正: 同じユーザー・グループの取得済み表示と選択月をタブ間で保持し、更新確認は表示を残して行う。非表示中の取得は停止する。権限喪失・退会時の共有データ破棄を維持する。

### P2: ホームで受信済みの活動を一覧で待ち直す

[再現画像](images/group-list-reload-pending.png)。[workspace.tsx](../../../frontend/src/features/v2/workspace.tsx) と [group-screen.tsx](../../../frontend/src/features/v2/group-screen.tsx) は同じ `/groups/today-activity` を別々のuseResourceで取得する。ホームの受信後に一覧へ移ると、再取得の応答が来るまで人数を表示できない。

採用した修正: 同じ共有範囲で取得したデータを画面間で引き継ぎ、更新確認中も人数を表示する。ユーザー・参加グループが変わった際には引き継がない。既存#78はホーム内の通信集約で閉じており、この画面間の引き継ぎ不足とは対応範囲が異なる。性能全体は既存#11と関連する。

### P3: 終了確認を閉じるだけで週間履歴を再取得する

[use-finish-week-records.ts](../../../frontend/src/features/session/use-finish-week-records.ts) はfinishOpenをeffect依存に含むが、閉じた場合の分岐がない。保存・日付変更なしでも、開始時1回、開いたとき2回目、戻ったとき3回目のGETを観測した。

閉じた後の再取得は表示のために不要な通信候補。表示が空になる現象や、実機で他の通信を遅らせる程度までは今回計測していない。開く際の更新確認は既存の意図があるため、確認なしに全ての再取得を停止する提案にはしない。

### 追加調査の検証

調査用E2E3件を確認。初回はサンドボックス内のローカルサーバー疎通でタイムアウト。実行環境を調整後、P1・P2成功、P3は調査側のボタン名誤りで失敗。正しい「トレーニングに戻る」へ修正してP3単独成功。架空データのみで、本番・実機のネットワーク性能は未計測。

## 1. 今日のメモと履歴のメモが接続されていない

### 通常操作

1. トレーニング開始→ベンチプレスで1セット追加。
2. 今日のメモへ「今日のベンチは肩が痛かった」と入力しEnterで保存。
3. メモPUT成功を確認してから終了する。
4. 再読み込み→履歴→同日の全メニュー→メモ。

履歴のメモ欄は空だった。保存した種目別メモはサーバー側の別データとして残る設計なので、データが削除されたとは判断しない。本人が終了後に読み返す導線がないことが問題候補。

根拠: [記録中の種目別メモ](../../../frontend/src/features/session/session-screen.tsx) は `/sessions/{id}/exercise-memo?name=...`、[履歴のメモ](../../../frontend/src/features/training/workout-memo.tsx) は `/workouts/{id}/memo` を読む。保存先テーブルも `gotore_session_exercise_memos` と `gotore_workout_memos` で別。履歴はsnapshotの種目別メモも表示していない。

[再現画像: 履歴の空のメモ欄](images/saved-today-memo-history.png)

### 通信失敗時

今日のメモPUTを503にすると本文はユーザー・セッション・種目別の端末キーに残る。しかし終了確認へ渡す未保存判定は数値入力の `input.dirty` だけで、メモの状態を渡さない。履歴は別キーを読むため、この本文を復元して再保存する入口がない。

[再現画像: メモ送信失敗後の終了確認](images/unsent-memo-finish.png)

#70の再開か、現在の種目別メモと履歴の接続として新Issueに分けるかは、ユーザーが問題と判断した後に整理する。履歴メモと種目別メモを無断で統合・共有する変更はしない。

## 2. 削除送信後のキャンセルが取消に見える

グループ設定→削除確認→「削除する」でDELETEを送信し、応答だけを保留した。削除ボタンは無効になるがキャンセルは有効なままで、押すと確認画面が閉じた。応答を再開するとDELETEは完了した。

単なる「確認を閉じる」と処理の取消が同じ「キャンセル」に見え、通信が遅いときに誤解する。削除送信中に閉じる・背景タップも防ぐか、送信が継続することを明確にする必要がある。サーバーで確定した削除を取り消せるとは判断しない。

[再現画像: 削除送信中でもキャンセルが有効](images/group-delete-pending.png)

[対象コード](../../../frontend/src/features/v2/group-screen.tsx) の削除確認は確定ボタンだけ `disabled={busy}`、キャンセル・SheetのonCloseは無条件。同形の退出・メンバー退出も同じ構造だが、今回の保留応答による動的再現はグループ削除だけ。

## 3. オーナー変更の確認がない

グループ設定→対象メンバーの三点メニュー→「オーナーにする」を押すと、すぐに `/groups/{id}/owner` のPATCHを送信した。削除や退出のような対象確認・キャンセル・確定の画面は出ない。

[設計資料](../../design/group-screen.md) は「オーナー移譲は確認してから確定する」としている。元のオーナーは権限を失う操作なので、対象を確認する段階の不足として優先度を高くした。

[再現画像: そのまま確定する管理メニュー](images/owner-transfer-before.png)

## 4. ダーク外観の編集中セットがほぼ見えない

設定→外観→ダーク→1セット追加→セット1を編集。選択背景は `rgb(255,245,245)`、重量・回数の文字は `rgb(245,245,247)`。実画面で数値がほぼ読めず、計算上のコントラストは約1.018:1だった。

[再現画像](images/dark-editing-set.png)

[対象CSS](../../../frontend/src/app/v2.css) の `.current-set-selection::before` が固定の薄いピンク、文字はダークテーマの `--text`。選択状態のデザインをダーク外観に対応させる候補。共通基準の通常文字4.5:1にも達していない。

## 7. CIと既存テストの確認範囲

[CI設定](../../../.github/workflows/ci.yml) は `make test-e2e-ci` を呼ぶ。[スクリプト](../../../frontend/package.json) の対象は recording-style・record-snapshot・first-set-defaults・record-loading の4ファイル。全E2Eではない。以前の「全E2Eを含むCIが成功」という報告は誤りであり、今回訂正した。

既存の関連27件を実行し、24件成功・3件失敗。失敗をアプリ不具合の証明として一括扱いしない。

- memo-recoveryの2件: `getByLabel("今日のメモ")` がsectionとtextareaの2要素に一致し、テスト側の指定が曖昧で停止。メモ保護の検証まで進んでいない。メモの候補1は別の調査スクリプトで確認した。
- settings-uiのグループ名変更1件: 現行のグループ設定操作に合っていない導線・期待で停止。アプリの名前変更が不可能だと判断していない。
- 成功した範囲: 終了確認の集計・遅延・失敗、メンバー退出・本人退出・三点メニュー、終了復帰と再起動、プロフィール失敗復旧、外観設定の保持、背景保存・終了の自動再送等。
