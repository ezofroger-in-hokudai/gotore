# 読み込み速度の改善（#11）

ユーザー報告は「毎回・全画面、特に過去の記録が遅い」。SupabaseはMumbai。本件ではユーザー指定によりリージョン・契約は変更せず、実装側を比較する。

## 維持する動作

- Authへの本人確認は毎回行う。接続だけを再利用し、ユーザーのCookie・認証ヘッダー・認証結果を別要求へ使い回さない。
- DBは毎回本人・グループ所属を確認する。共有データのCDNキャッシュは使わず、APIはno-store。
- 表示名が変わらない場合はSELECTだけで返す。未作成・変更時は従来のUPSERTと競合処理で同期し、Auth未設定時の既存名を保持する。
- ホームの5秒更新、非表示停止、失敗後の再試行、保存・編集・削除時の更新を維持する。

## 過去の記録の再訪

初回実装では自分の記録一覧だけを、ログイン中の画面のメモリに最大5ページ・60秒保持する。URL（日付・ページを含む）ごとに区別し、保存・編集・削除などrefreshKeyの変更で破棄する。別ユーザーのログインではWorkspaceを作り直すため共有しない。localStorageや共有一覧には保存しない。

再訪時は前回の内容をすぐ表示し、「更新中…」とともに必ずAPIで再確認する。成功時に置換する。#111の追加採用により、一時的な失敗は一覧を保持して更新失敗と再試行を表示し、権限喪失・削除等は消去する。長時間経過後・新しいページでは従来どおり取得を待つ。初めて読む履歴の短縮はAPI側の改善で行う。

## 計測

APIのServer-Timingに数値だけを付ける。

| 名前 | 範囲 |
| --- | --- |
| auth | Supabase Authへの往復 |
| db_connect | DB接続の確立 |
| profile | 本人プロフィールの確認・必要時の同期 |
| app | middlewareからレスポンス開始まで（上記を含む） |

URL・トークン・SQL・個人情報は計測ヘッダーへ入れない。appはコールドスタート、インターネットの往復、本文の転送・描画、依存の後処理を含まない。appと各区間を足し合わせない。

本番ではブラウザのNetworkでworkoutsの待ち時間とServer-Timingを比較する。記録10件・50件、初回・再訪、同一回線で各5回以上を分けて記録する。healthだけで認証済み画面の改善率を判断しない。

## 一般的な高速化手法の確認と追加適用（PR #64）

2026-09-09のユーザー依頼で公式資料を確認した。今回の選択は以下のとおり。

当初はDBプールを保留していたが、今回の「一般的な方法を調べて適用」の追加指定により、上限を設けたローカル比較を実施して採用した。

| 手法 | このアプリでの扱い |
| --- | --- |
| 接続を再利用する | HTTP接続は適用済み。DB接続は毎回作成していたため、今回Psycopgの公式pool拡張を追加 |
| 通信・SQLの往復を減らす | セッションSQLの集約と不要な履歴取得の省略は本PRの前半で適用済み |
| キャッシュ・先読み・必要な画面だけ取得 | ユーザーごとの画面内キャッシュと種目候補の先読みを維持。最高記録の一覧判定も一覧を開いたときだけまとめて取得 |
| 遅いSQLを計測し索引などを調整する | EXPLAINで実行計画を確認する方法を調査。今回、索引不足を根拠なく仮定したmigrationは追加しない |

参照: [Psycopgの接続プール](https://www.psycopg.org/psycopg3/docs/advanced/pool.html)、[Supavisorとアプリ側プールの併用](https://supabase.com/docs/guides/troubleshooting/supavisor-faq-YyP5tI)、[Next.jsの最適化](https://nextjs.org/docs/app/guides/production-checklist)、[PostgreSQLのEXPLAIN](https://www.postgresql.org/docs/current/using-explain.html)。

アプリ起動・終了に合わせてDBプールを開閉する。`DATABASE_POOL_MAX_SIZE`は既定4（プロセスごと、0〜10）、最小0、未使用30秒、最大寿命300秒、待機5秒・最大16要求とする。0にしてAPIを再起動すると毎回接続する従来方式へ戻せる。インスタンス数が増えると合計接続数も増えるため、この値はDB全体の上限ではない。SupabaseのTransaction Poolerの接続文字列を維持し、prepared statementは無効のままとする。

貸出前の生存確認で切断済み接続を交換し、処理後はcommit/rollbackを終えて返却する。本人・グループの認可は要求ごとに実施し、接続へユーザー別の状態を設定しない。実行中の保存失敗は自動再実行せず、既存のrevision付き再送で扱う。上限・待機超過は503と短い再試行案内を返す。`Server-Timing`の`db_connect`にはプールの待機・貸出確認も含む。

専用`_test` DBで次を実行する（SELECTのみ、schema変更なし）。

```bash
TEST_DATABASE_URL=専用テストDBのURL backend/.venv/bin/python scripts/benchmark_connections.py --samples 8
```

接続確立に120ms・各SQLに40msを加え、実PostgreSQLの接続取得とSELECT 1を比較した。プールの貸出前チェックもSQL遅延に含む。

| 方式 | 初回 | 継続8回の中央値 | 9要求の接続数 |
| --- | ---: | ---: | ---: |
| 毎回接続 | 168.6ms | 167.2ms | 9 |
| 接続プール | 210.1ms | 82.6ms | 1 |

継続時の取得を減らせるため適用する。初回は生存確認が増える分だけ遅くなる。Auth・実回線・アプリ全体・本番のコールドスタートは含まないため、この約51%減を画面全体や本番の改善率として使わない。遅延なしで確認する場合は`--connect-delay-ms 0 --sql-delay-ms 0`を付ける。

## #79: 非表示の記録画面への比較・BEST取得を延期

記録画面が非表示の間は、セット保存が確定しても種目の比較情報・全セット一覧のBESTを再取得しない。再訪時に最新の確定revisionで再取得する。同じ種目の比較は再確認中も保持し、種目メモと今回のメモの下書き、送信待ちキュー、生存確認は継続する。別の種目の値は表示しない。

2026-09-10、Linux/Chromium・390×844・mockTrainingで、PATCH応答を保留→ホーム／設定へ移動→保存成功の順で比較した。修正前は非表示のcontext要求が1回、修正後は0回。記録へ戻ると1回取得する。全セット一覧も非表示での保存完了後の再取得は0回で、戻るとrevision 2のBESTを取得する。

再訪のGET応答を保留しても前の比較値とメモ入力を表示し、応答後に新しい比較へ置換することをブラウザで確認した。表示時間の実測比較・本番での改善率は未測定。保存APIそのものの処理時間やキューの送信量は本変更では改善していない。対応テストは `frontend/tests/e2e/session-performance.spec.ts`。

## #74: 一覧の読み取り待機期限

`useResource`からの読み取りは、認証セッションの取得から本文の読み取りまで15秒を上限とする。時間内に完了しなければ要求を中断し、「読み込みに時間がかかっています。再試行してください。」を表示する。一度取得した同じ一覧は保持し、更新失敗と再試行を示す（#111）。手動再試行または次の5秒周期で新しい要求を開始でき、期限切れの応答は採用しない。画面移動時は期限のタイマーと要求を終了する。

15秒は既存の5秒更新の3周期分。14秒で返る正常応答を受け取り、未完了中は要求を重ねないことをブラウザテストで確認する。保存・画像送信・同期キューの再送方式は、この読み取り用の待機期限の対象外。

## #93: 閲覧・記録・履歴の表示待ちを減らす

2026-09-11のユーザー指定により、表示中の仲間の詳細を先読みし、LIVE中の記録を優先する。先読みは選択中のグループの画面内・近傍に限定し、同時2件まで。ログイン中のFeed内メモリに最大20件・60秒保持し、更新日時が変わった記録は取り直す。終了済みで更新のない記録の本文を5秒ごとに取り直さない。

詳細を開くと取得済みの内容をすぐ表示し、APIで再確認する。先読みと開く操作が重なった要求は共用する。表示中のLIVE記録は5秒ごとに更新し、終了済みはフィードの変更時・表示復帰・開き直しで再確認する。開いた記録が新しい記録に置き換わって最新フィードから外れた場合は、フィードだけで共有解除・削除を追えなくなるため、詳細APIを5秒ごとに確認する。#111によりフィードは一時失敗時に前回の内容を表示し、未確認表示と再試行を付ける。個別の共有記録詳細は従来どおり失敗時に隠す。どちらも所属・共有解除・削除の確認を維持する。別グループ・別利用者へ流用せず、画面離脱・非表示タブでは先読みを停止する。

ホームが表示できた後の余裕がある時間に、本人の履歴1ページと選択月のカレンダーを準備する。記録中や保存処理中はその先読みをしない。履歴へ入ったら保持内容を表示しながら再確認し、一時失敗時は前回値と更新失敗を表示し、権限喪失・削除等では消去する（#111）。

ホームから記録画面への遷移は復元通信を待たない。開始・保存は従来どおり復元と開始成功の確認後に許可する。端末へ保存済みのセット追加は既存のバックグラウンド同期を使い、サーバー応答前に同期済みと表示しない。

## 開始入力と種目比較の先読み（#95）

- 開始ボタンを押すと直ちに通常の記録入力画面へ移り、開始APIと比較情報を並行して読み込む。重量・回数や種目変更はその画面で操作でき、開始確定で画面を作り直さずフォーカスと入力を保つ。開始前の種目・重量・回数の入力は、#102の追加指定で表示しない。開始押下後は種目選択へ即時移動し、選択後に通常入力画面へ進む。開始失敗時は入力を保持して同じ開始IDで再試行する。開始成功後は入力を引き継ぎ、既存セッションの端末入力があればその復元を優先する。開始確定前にはセット保存・成功表示を行わない。
- 記録画面を表示中、選択した種目と候補の先頭3件の前回比較・BEST・種目メモを優先順に取得する。開始待ちはセッションIDを付けずに本人の比較情報を取得し、開始確定後は実際のセッションIDを付けて前回記録の基準を再確認する。異なる既存セッションが返った場合は、そのセッションの入力・比較へ切り替える。先読み目的でトレーニングを開始しない。
- 同時取得は2件、保持はセッションごとに5種目、再取得を省略できる期間は60秒。選択時は取得済み／取得中の情報を再利用する。画面・タブ非表示で取得を止め、保存確定・メモ変更・表示復帰時は再確認する。更新中は選択中の比較を保持し、失敗時は古い情報を隠して再試行を表示する。
- 開始通信自体の短縮や、開始未確定のセットを自動保存する変更は含めない。開始待ちの入力は画面内で保持し、再読み込みを跨ぐ復元は確定後のセッション入力を対象にする。

## 開始前の振り返り（#102）

2026-09-12のユーザー追加指定により、開始前の種目一覧と重量・回数入力を削除する。「トレーニングを開始」を押すと開始通信を待たず種目選択へ進む。選択後は従来どおり通常の入力画面で比較を読み込み、開始確定までは保存を無効にする。失敗時の入力保持・同じ開始IDの再試行と、既存セッションの復元優先を維持する。

## 一時的な再取得失敗時の表示（#111）

ネットワークエラー・読み取り待機超過・408/429/5xxでは、同じ取得先の表示済みデータだけを保持する。「更新できませんでした。前回の内容を表示しています。」と再試行を表示し、再試行成功時に最新値へ置き換える。LIVEの人数・バッジは再確認できるまで最新状態として表示しない。初回取得失敗は以前と同じくエラーで、空の実績として扱わない。

401/403/404等の一時障害ではない4xxは、対象リソースの保持ページと表示内容を消す。分析も同じエラー分類を使い、別期間のキャッシュを消す。アカウント切替は従来のWorkspace破棄で分離する。別URL・別グループ・別月を現在の値として代用しない。保持中の値の取得時刻は更新失敗で延長せず、再試行中に同じ表示を落とさない。

対象は共通useResourceと分析キャッシュ、および履歴・活動カレンダー・グループ一覧/詳細/フィード・分析の表示。共有記録の個別詳細のキャッシュは従来どおり失敗時に内容を隠す。非表示時の停止、取得頻度、最大保持件数、メモリ限定は維持する。
