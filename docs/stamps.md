# スタンプ（#12）

ユーザーが2026-09-15に採用したB案（選択パネル）と推奨①（記録中に5秒表示＋未読）を実装する。

- 種類は👏おつかれ！・🔥ナイス！・💪一緒にがんばろう・👀見たよ。本人の記録にも送れ、受信一覧・遅延表示で他者からの反応と同じように確認できる。1記録・1送信者・1種類につき1個。複数種類を併用でき、取消できる。送信成功前に件数を確定しない。
- グループは記録を探す・表示するためのまとまりであり、スタンプの保存先ではない。同じ記録を閲覧できる全グループで、同じ反応・送信者・件数を表示する。記録者が所属しない、または記録が共有されていないグループには、記録もスタンプも表示しない。
- 保存済みセットのある記録が対象。トレーニング中も送れる。編集後は保持。記録削除、または全共有先の解除で対象反応を除去する。スタンプを送った後に送信者がグループを退会しても、同じ記録を閲覧できる範囲では反応を保持する。
- 受信一覧は50件ずつ。表示したIDだけ既読にする。5秒表示を済ませた状態と、一覧で確認した既読を分けてサーバー保存する。同じ送信の再送で新着を増やさず、取消後の新しい送信は別の反応として扱う。
- 記録画面を開いている間は今回の記録の受信を定期確認。5秒だけ名前とスタンプを表示し、以後は未読件数を残す。入力値・フォーカス・入力欄の位置を保つ。複数件はまとめて表示。一覧はタップ時だけ開く。
- 終了後にも今回の反応を確認できる。アプリ非表示中は取得を停止し、復帰時に再確認する。Push通知、音、振動は今回含めない。配信即時性は保証しない。

本実装ではAPIの認可・DBの整合性を検証し、機能の公開前にmigrationを適用する。採用プレビューは別のローカル文書に保持。最新の実行結果はprogress.md/PRに記録する。

## APIと取得範囲

| API | 用途 |
| --- | --- |
| `GET /groups/{group_id}/workouts/{workout_id}/stamps?offset=0` | 対象の反応を50件ずつ、総数・人数・自分の種類・送信可否を取得 |
| `PUT /groups/{group_id}/workouts/{workout_id}/stamps/{kind}` | 同じ種類の送信を冪等に確定 |
| `DELETE /groups/{group_id}/workouts/{workout_id}/stamps/{kind}` | 本人が送った種類だけ取消 |
| `GET /stamps/inbox?group_id=...&workout_id=...&offset=0` | 本人宛ての受信一覧。groupは表示できる記録の絞り込みであり、スタンプの絞り込みではない。workoutは任意 |
| `POST /stamps/seen` | 表示済み/既読をID単位で保存（最大100件） |

いずれも `/api` 配下、認証必須。共有記録の取得と送信は、操作時点で閲覧者・記録者が同じ表示グループに所属し、記録がそのグループへ共有されていることをロックして確認する。反応の取得・集計はこの閲覧確認の後に記録単位で行う。外部入力は型・固定種類を検証しSQLへバインドする。新規テーブルはRLSを有効にし、anon/authenticatedの直接アクセスを拒否する。

通常のフィードではスタンプボタンだけを追加し、反応一覧はパネルを開いたときに取得する。開いているパネルと記録中の受信確認は10秒周期。非表示タブでは止め、復帰時に再取得する。グループ数に比例した常時取得は行わない。通知の表示済み保存が失敗した場合は再試行を出す。

## 2026-09-18 採用A案（#179・#171）

ユーザー採用の直接リアクションへ変更する。カードと共有詳細に高さ30pxの角丸スタンプ・件数、＋、…を置く。48pxのタップ領域を維持。＋は💪がんばれ・🔥まだまだ・👎バッド・🤩すごい・👏えらい・👺天狗の6種類を絵文字だけで選ぶ。詳細・選択シートでは閉じるまで端末上の選択を切り替え、閉じる時点の最終状態を送る。古い4種類のID/意味/反応は保持し、既存反応の表示と取消を継続する。オリジナル登録は今回含めない。

本人・グループ・記録・種類をキーに送信状態を画面から分離し、一覧と詳細で共有。押した時点で仮の件数/選択を出すが、通常の送信待ちは表示しない。失敗時は確定値へ戻して再試行を出す。PUT/DELETEの成功と再取得失敗を区別する。閉じても処理が継続し、未完了は端末へ保存して再訪時に確認・再試行できる。OS終了中の実行は保証しない。権限喪失は送信を止め、未確定を成功扱いしない。

表示中の記録だけをグループ別・最大50件の一括集計で取得し、件数を送信者一覧の最初の50件から計算しない。非表示タブでは定期取得しない。種別拡張migrationをアプリ/APIより先に適用する。具体的な検証・制約はprogress.md/PRで追跡する。

実装はアプリ内の画面移動中の送信継続を対象とする。ブラウザ終了後の送信は保証しない。送信待ちはユーザー別・操作別のlocalStorageに保存し、再起動後は確認して再試行する。復元時は状態を照合し、既に反映済みならPUT/DELETEを繰り返さない。詳細内では同じ種類を何度でも切り替え、閉じた時点の最終状態だけを送る。他の種類・画面も操作を止めない。再取得は10秒ごと、非表示タブでは停止。非表示の古い記録キャッシュは200件を目安に破棄し、表示中・送信待ちを優先する。

本番は `supabase/migrations/20260918150000_inline_stamp_kinds.sql` を先に適用してからアプリ/APIを更新する。既存データの変換・削除はない。旧種類も一覧と取消に残す。画面画像は `docs/images/inline-stamps/`。

## トレーニング中の受信表示（2026-09-18追加指定）

記録中の大きい受信ボタンを、カードと同じ小さな角丸の絵文字＋種類別件数に置き換える。件数は受信APIの全件集計 `counts` を使い、最初の50件から計算しない。同じ記録は複数グループから開いても、同じ反応を一度だけ数える。自分への送信操作は追加しない。絵文字のタップと右端の…で、既存の受信詳細を開き、誰から届いたかを確認する。

## 2026-09-25 記録単位への統合

スタンプを「グループ内の反応」ではなく「記録への反応」に変更する。`20260925010000_global_workout_stamps.sql` は、同一の記録・送信者・種類で既に複数グループに保存されている行を一件へ統合し、未確認が一件でもあれば未確認のまま残す。その後、グループ列とグループを含む一意制約を外し、`(workout_id, sender_id, kind)` を一意にする。

APIのURLに残る `group_id` は、記録を開く権限と表示経路の確認だけに使う。別の共有グループから同じ種類を送っても二件目は増えず、取消もすべての表示経路へ反映する。受信一覧のグループ指定も、記録の表示範囲だけを絞る。記録者が所属しないグループはAPIで対象記録を取得できないため、スタンプだけが漏れることはない。

新着は5秒間の枠の強調と読み上げで知らせ、絵文字と件数はその後も残す。送信者名の一時表示は詳細へ集約する。未読は…の小さな印と読み上げで示し、詳細で実際に表示した反応だけを既読にする。多種類は一行の横スクロールで、…は固定し、入力位置・セット一覧の高さを変えない。0件は「スタンプなし」、未取得はスピナー、失敗は同じ行の再試行操作とする。追加指定により、終了後の受信欄、ホーム/グループの受信入口も共通の絵文字＋件数・…表示に統一する。送信者一覧と選択対象の枠も角丸にする。記録画面の終了ボタンは省略せず「トレーニング終了」と表示する。

## 2026-09-25 詳細内のまとめ送信

仲間の記録詳細とスタンプ選択シートでは、タップのたびに通信を待たない。選択は即時に赤い背景・赤い輪郭・チェックで示し、同じ種類も何度でも切り替えられる。詳細または選択シートを閉じると、その時点の最終状態だけをバックグラウンドで送信する。元の状態へ戻した種類は送信しない。

通信中のスピナーや操作の無効化は通常表示しない。失敗・権限喪失・端末保存失敗だけは、閉じた後も送信待ちとして保持し、復旧操作を出す。詳細外の直接スタンプは、従来どおり画面を止めずにバックグラウンド送信する。

## 2026-09-25 記録詳細の表示位置

記録詳細のシート見出しは「記録の詳細」ではなく記録日だけにし、本文で日付を重ねない。記録者アイコンは進行中なら赤いLIVEドット、最高記録を含むなら炎で状態を示し、文字の「トレーニング中」は表示しない。スタンプ操作は記録者名や日付ではなく、総負荷・セット数・時間の要約直下に置く。今日の仲間には本人も含め、本人の記録でもスタンプを送れる。本人宛ての反応は他の反応と同じ受信一覧・遅延表示で扱う。

## 2026-09-25 共通カードの常設スタンプ

ホームの時系列、グループから開く共有記録、履歴の共有記録、トレーニング中に開く仲間の記録では、同じ `StampControl` を使う。`💪 🔥 👎 🤩 👏 👺` の6種類を最初から同じ順序で表示し、追加用の `＋` を経由しない。選択中は共通の赤い選択表示とチェックを使い、同じ種類を再度押すと取り消す。

選択ボタンとスタンプ詳細には「がんばれ」「えらい」などの日本語の意味説明を表示せず、読み上げ名も `💪スタンプ` のような中立表現にする。既存データの種類IDと受信互換性は維持する。
