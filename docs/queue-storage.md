# 送信待ちデータの差分保存（#77）

ユーザーの高速化継続指定に基づき、端末保存量を減らす。操作ごとの保存・共有・BEST判定とrevisionの順序は維持する。

## 保存と送信

確定済みのセッションを基準にし、未送信操作はIDと順序付きの差分として保存する。同じ種目のセット追加/訂正/取消はセット列の差分、種目追加/削除/並べ替え/複数種目の更新は種目列の差分を使う。変更しない前後の要素を再保存しない。差分の範囲と値を検証し、復元不能なら元の文字列を保持して停止する。

端末への書込み成功後に表示を更新する。送信時は先頭操作から、従来と同じ全種目・全セットへ復元して既存PATCH APIを呼ぶ。操作を間引かず、応答のid・revision・セット内容が送信結果と一致した場合だけ先頭を除く。ACK待ち中の末尾追加は同じstoreロックで読み直して保持する。

通信ロックと保存ロック、ユーザー別キー、複数タブのrevision照合、応答喪失後の同じ要求の再送を維持する。終了は全未送信の反映後、BEST・共有はサーバー確定後。API・DB・送信本文は変えないため、ネットワークの全量送信削減は今回の効果に含めない。

## 旧形式と失敗

既存の `gotore:session-queue:v1:<userId>` キーを使い、JSON本体に `version: 2` を付ける。キーを移動しないため読取・削除・複数タブのロックが分断されない。旧形式はversionなしの基準＋各操作の全状態で、操作IDと順番を保って読める。読取だけでは書き換えず、次の保存またはACK確定時に1回の書込みで新形式へ移る。移行時の容量不足でも旧文字列を消さない。

新形式の待機操作には旧形式の `exercises` を置かない。旧クライアントは読取検証で拒否し、差分を空の全状態として送信しない。待機データがある間は旧画面で続行せず更新後の画面を使う。待機が空の形式は旧画面でも読める。旧新タブ間で書込み前に共有キーを読み直すため、古いrevisionの操作は拒否される。

未対応version・重複操作ID・範囲外差分・不正数値は送信/上書きせず保持する。容量不足、通信失敗、サーバー結果不一致でも未送信を残し、確認なしで別端末の内容へ上書きしない。

## 検証・限界

旧形式からの移行、150セットと訂正/取消の全送信内容・順序、ACK中追加、応答喪失、ACK保存失敗、移行時容量不足、複数画面、破損/未対応形式を検証する。ブラウザでも旧データの読取保持→新形式へ追加→再起動→再送を確認する。

`frontend/scripts/benchmark-session-queue.ts` は30/150/600セット（1種目30セット）、先頭訂正と末尾取消の列を比較する。各方式1回ウォームアップ後5回、保存量と送信本文量、直近30追加・訂正・取消の中央値を記録する。メモリへの文字列保存なので実localStorageのI/O・端末の描画・実回線速度ではない。実機の長い送信待ち・終了待ちと、送信量削減は#77で継続する。
