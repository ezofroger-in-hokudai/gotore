# 本人データの端末保存方針（#185・#231）

2026-09-29の相談で、本人データを端末にも保持する方向と、実装より先に保存・同期の方針を整理する順番を決めた。この文書は実装前の設計案であり、各段階の受け入れ条件を確認してから着手する。

## 解決したい操作

種目を選ぶと、前回記録の取得前に仮の20kg×10回のホイールが開く。遅れて前回値が届くと、未操作のホイールが別の数値へ変わる。利用者が前回を基準に記録したいとき、この表示順では判断しづらい（#231）。以前に読んだ本人の記録を端末から先に表示できるようにする（#185）。

端末保存だけでは、初めて使う端末、ブラウザデータを消した後、別端末で直近記録を追加した直後に前回値が必ず手元にあるとは限らない。これらの状態でも、仮の数値を前回値として見せて後からホイールを無断変更する動作をなくすことを、#231の独立した受け入れ条件にする。

## 現状

| データ | 現在の保持 | 今後の端末保存案 |
| --- | --- | --- |
| 進行中のセット・終了意図 | ユーザー別localStorageキュー。送信と競合保護あり | 既存キューを維持し、確認済み記録の保存と混同しない |
| 未確定入力・メモ下書き | ユーザー・対象別localStorage | 復元を維持し、保存済みの本文と状態を分ける |
| 保存済みの本人記録 | サーバー正本、画面内メモリは最大5ページ・60秒 | すべての本人記録とセットを端末に保存する |
| 本人の種目・記録メモ・種目メモ | APIと画面内保持 | 本人の内容を端末に保存する |
| 本人プロフィール・画像・設定 | API、一部の端末設定はlocalStorage | 本人の情報を端末に保存する。画像の容量と更新方法は実装前に決める |
| 仲間の記録・グループ集計 | APIと短時間の画面内保持 | 今回の永続保存対象には含めず、権限確認後に取得する |

現行の`GET /workouts`は50件単位のoffsetページ、`GET /exercises/context`は種目ごとの前回・BEST等を返す。前回値の意味はAPI側の業務ルールに従い、画面内で別の規則を作らない。現在のメモリ保持や未送信キューの詳細は[読み込み仕様](loading-performance.md)と[送信待ち保存](queue-storage.md)を参照する。

## 正本と表示

- サーバーで確定した本人記録を正本とし、端末の確認済み記録は読み取り用の複製とする。未送信キューは端末で受け付けた操作として別に保持し、サーバー確認前に「同期済み」と表示しない。
- 認証済みの同じユーザーに、端末の完全な保存済みデータがある場合はそれを先に表示し、背景でサーバーと照合する。別ユーザーの保存領域を画面へ渡さない。
- 保存済みデータがない・不完全・古い場合は取得を待つ状態を明示する。#231では前回値が確定するまで仮の20kg×10回を「前回を引き継いだ入力」として表示しない。手入力を始めた後や保存後に届いた応答はホイールを無断変更しない。
- 別端末の追加・編集・削除を反映し、削除済み記録を古い端末から復活させない。全件取得途中に失敗した場合は、不完全な一覧で端末の完全なスナップショットを置き換えない。

## 保存先と故障時の扱い

確認済みの全記録など大きな構造化データは、ブラウザ標準のIndexedDBを候補とする。既存のlocalStorageキューは同期順序を保つまで移さない。保存層は`frontend/src/lib`等に閉じ、画面とAPIの業務規則から分ける。新しいライブラリやモバイル基盤の導入は前提にしない。

Webの端末保存には容量制限・自動消去・利用者によるブラウザデータ削除がある。[WebKitの保存方針](https://webkit.org/blog/14403/updates-to-storage-policy/)と[MDNの保存領域の説明](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)を前提に、端末保存を唯一の正本と約束しない。保存失敗や容量不足では古い完全なデータを壊さず、オンライン取得で復旧できるようにする。`navigator.storage.estimate()`・永続化要求の採否とiPhoneホーム画面アプリの動作は実機で測る。

ログアウト・アカウント切替時は本人の複製を端末から消す案とする。未送信キューを消すと記録を失うため、その状態のログアウト操作と復旧方法は実装前に決める。ブラウザの同じoriginを使う他の人へ、以前のアカウントの記録を表示しない。

## 段階と確認点

1. **保存契約**: 本人データの一覧と更新・削除を取りこぼさないAPIの基準値を決める。現行のoffsetページだけで全件を取得すると、取得中の追加・削除によって重複や抜けが生じ得るため、一貫したスナップショットまたは変更カーソルを設計する。既存DB・APIの変更要否をここで決める。
2. **本人の読み取り複製**: 全本人記録、種目、メモ、プロフィールをユーザー別に端末保存する。初回・再訪・再起動、ページ途中失敗、容量不足、ログアウトを確認する。サーバー確定済みの内容だけをこの複製へ入れる。
3. **前回値とホイール**: 種目選択前に端末の本人データから前回値を準備し、#231の表示順を直す。端末に前回値がない場合は確認中と手入力を区別し、遅い応答が入力・保存済みの数値を変えない。冷起動、別端末更新、オフラインで検証する。
4. **更新の収束**: 編集・削除・別端末更新を保存複製へ反映する。現行キューと競合解決を照合し、削除の復活、メモの漏れ、応答喪失時の重複を防ぐ。

最初の実装単位は上の1と2に分ける。#231の画面修正は3として追跡する。測定対象は初回同期時間、端末保存後の再訪・再起動から前回値表示まで、API要求数、端末使用量とする。

## 実装前に決めること

- 前回値が端末にもAPIにも未取得の間、ホイールを待機表示にするか、利用者の明示的な手入力を先に許すか。どちらでも仮の値を前回値のように見せない。
- 本人のプロフィール画像の保存形式・容量上限・更新方法。分析など再計算できる値を、元データから作るか複製として持つか。
- ログアウト時に未送信操作がある場合の扱いと、端末保存失敗時の復旧案内。
- 全件の一致を確認するAPI契約、別端末削除を伝える方法、データが増えた場合の同期時間の上限。
