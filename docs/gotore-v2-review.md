## 結論

画面構成は現行のNext.js・FastAPI・Supabaseを生かして実装できる。ただし、資料をそのまま実データへ接続してよい状態ではない。特にセット単位の保存と共有開始、セッションの開始・終了、LIVE、BESTの計算条件は画面だけで決められない。

下記は「既存と違うため実装できない」という評価ではなく、v2を動く機能にするための不足条件を整理したもの。新UIの採用による表示変更、既存ルールで補える事項、追加合意が必要な業務変更を区別する。推奨案は未承認であり、既存仕様を上書きしない。

## 1. 実装前に判断が必要な点

| 対象 | 確認した差分・問題 | そのまま接続した場合の影響 |
| --- | --- | --- |
| 保存と共有 | 現行は1ワークアウトを一括保存し、保存直前に1グループまたは自分だけを明示。v2はセットごとに保存するが共有先を選ぶ導線がない。共有範囲自体が未確定と明記されている | ホームの表示グループを共有先に流用すると、カード切替で意図せず記録を公開する。個人記録を後から共有する場合も現行PATCHでは不可 |
| セッション | 02・05〜10は既にトレーニング中の状態。開始・終了・破棄の操作が33画面にない。現行DBに開始/終了時刻・進行状態はない | いつ履歴へ確定するか、LIVEを減らすか、次のトレーニングを始めるか判断できない。48分などの時間を既存created_atから復元できない |
| LIVE / TODAY | 現行は共有済み記録の5秒更新のみ。LIVE信号・切断時の期限・日付を跨ぐ集計・所属変更時の条件は未定 | 単に最近保存した人数をLIVEにすると「現在トレ中」と一致しない。非共有の活動を人数やメンバー状態から漏らす可能性がある |
| BEST / 推定1RM | 既存の計算実装なし。式、回数の適用範囲、丸め、同値、初回、訂正・取消時の演出が未定 | 同じセットで画面ごとに異なる値、訂正後も残る偽のBEST、1000回まで認める入力から過大なRM表示が生じる |
| 前回と種目メモ | 履歴の種目は名前のスナップショット。候補IDへの参照はなく、同一ワークアウトに同名の種目行を複数保存できる。継続種目メモは未実装 | 候補削除・再追加で履歴やメモが切れる。同名行の一部だけを「前回全セット」として出す。記録単位の私的メモを誤って継続メモへ変換する |
| 通知 | 30には「仲間の記録や自己ベストの更新」とあるが、既存に通知配信・購読の仕組みはない | 設定をオンに保存しただけでは通知機能にならない。共有解除・ログアウト後の配信範囲も未定 |

### 推奨案A: セッション・共有・LIVE

1. 現行Webを継続し、1人の進行中セッションは1件にする。初回開始時に「自分だけ / 所属グループ1つ」を明示して選ぶ。グループを選ぶ場合は、トレーニング中の状態と保存済みセットが共有されることを開始操作前に伝える。閲覧中のグループと共有先は別に保持する。
2. セットの「記録」でサーバーへ保存し、選んだ共有先へ反映する。ホイール操作中や入力途中の値は公開しない。最初の保存後は共有先を変更しない。従来の「全体確定後に初めて共有」からの変更として承認を必要とする。
3. 種目一覧に「トレーニングを終了」を追加する。別タブ移動・再読み込み・ホーム切替は終了とみなさない。同日の次セッションも別IDにする。保存済みセットは終了前でも本人の履歴に「進行中」として参照でき、既存のセット数集計に含める。
4. 開始時刻・終了時刻を保存する。既存記録は完了済みとして扱い、所要時間は未計測表示。保存済み記録のcreated_atを開始時刻とみなさない。過去日の手入力は完了記録として保存し、今日のLIVEに入れない。
5. LIVEは未終了かつ直近5分以内の生存確認がある本人を、共有先でのみ数える案。表示中は30秒ごとに生存確認し、画面非表示中は停止。期限切れは「完了」ではなく通信未確認として扱い、再開できるようにする。休憩・画面ロックでLIVEから外れる限界は実機で評価する。5分・30秒は今回の提案値。
6. TODAYはJSTの日単位で、共有を許可した現在のメンバーを重複なく数える。開始後とセット保存時に当日の活動を記録し、日跨ぎでは新しい日の操作から数える。終了・LIVE期限切れでは当日の実績を消さない。退出時は既存ルールと同じく共有を解除し、再参加で自動復元しない。
7. セット保存・編集・取消には同じセッションIDとrevisionによる競合検知を使う。現行の全体POSTをセットごとに別IDで呼ぶ方法は採らない。既存JSONを維持するなら、種目/セットの位置と期待revisionを組にして対象を検証し、古い編集が別セットへ適用されないようにする。
8. 「元に戻す」は直前のセット追加だけを取り消す案。保存成功後だけ表示し、その後の保存や他端末更新と競合したら取り消さない。最後の1セットを取り消しても進行中セッションは保持する。既存モデルは0種目・0セットを許可しないため、進行中データの扱いを追加設計する。BESTと共有表示も再集計する。

「終了時にだけ共有」を維持する案も可能だが、進行中の具体的な仲間の記録を見せるv2の体験とは異なる。その場合はLIVEだけの公開同意と、完了時の共有確定を別々に設計する必要がある。

### 推奨案B: 前回・BEST・種目メモ

1. 初回は本人と前後空白除去後の種目名の完全一致で集計する。表記揺れを勝手に統合しない。候補を削除・再追加しても、同名の過去実績と継続メモは残す。同じセッションの同名行は保存順に全セットを参照する。今後の名前変更・器具別同定は別設計にする。
2. 「前回」は対象種目を含む直近の過去セッションを全履歴から取得する。日付・セッション開始順（旧記録は保存順）で区別し、編集中の記録を除外する。過去セッションを編集するときはそのセッションより前の記録を対象にする。表示中50件だけから選ばない。
3. 計算候補は、重量が正で1回なら重量そのもの、2〜10回なら `重量 × (1 + 回数 / 30)`、表示は小数1桁で四捨五入。0kg・11回以上はRMを算出せず「—」とする案。これは合意前の製品ルール案であり、資料の例だけで確定した式ではない。記録の保存可能範囲自体は狭めない。
4. 最高重量・最高RMは本人の全保存済みセットから別々に算出する。RM比較も表示と同じ丸め後の値で統一する案。同値は更新とせず、履歴がない初回は基準値の登録とする。追加保存による厳密な増加にだけ更新演出を出し、過去の訂正・削除・取消は再計算のみ行う。
5. グループのBEST表示は、そのグループに共有されたセットについてだけ返す。他グループや私的履歴の数値を応答へ含めない。本人の全履歴と比較したBESTであることは仕様として明示する。単なる現在値の首位と、保存時に更新した出来事は混同しない。
6. 種目メモは本人限定・0〜1000文字・明示保存・revisionによる競合検知を提案。候補とは独立して保持し、削除/再追加でも残す。既存の記録単位メモは変更せず、前回メモとして表示する場合も「セッションメモ」と明示する。

### 推奨案C: 設定と配信の範囲

名前変更は既存Auth/プロフィール同期を再利用。テーマは端末連動・ライト・ダークを保存する。振動は対応機能を検出して有効化し、使えない端末では利用不可と示す。振動APIはすべての主要ブラウザで利用できる機能ではない。[MDNのAPI仕様](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/vibrate)

Push通知は今回の実装から分ける案を推奨する。未提供の段階ではオンに切り替えられるUIを出さない。全33状態の完全実装が完了したとは扱わず、既存の通知Issue #21に対する残作業として明記する。今回含める場合は配信イベント・購読先・失効・公開範囲・運用設定まで実装対象となる。iOS/iPadOSではホーム画面Webアプリとユーザー操作に応じた許可要求という条件もある。[WebKitの説明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

## 4. 見た目の適用範囲

従来のdesign-system.mdは角丸0・数値20〜24px・通常390×720でスクロール不要を要求する。一方v2は角丸24/26・数値27/36px、記録画面390×907を基準とする。この寸法のまま720px高に配置すると全内容は収まらない。

今回の新デザイン依頼に合わせ、見た目はv2を採用し、旧数値を混在させない案。通常時も必要な縦スクロールを許可し、主要操作を触れる配置にする。文字拡大・キーボード・最大30セット・長い名前やメモでは必ず実画面で確認する。単に全画面を縮小して合わせない。旧来の「通常はスクロール不要」条件を継続する場合は、表示行数の切替など追加レイアウト設計が必要。
