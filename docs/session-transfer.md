# セット保存の通信量（#77）

高速化の継続指定に基づき、保存キューが送る全状態JSONを必要な場合だけgzip圧縮する。セットを省略・結合せず、保存順、expected_revision、応答消失時の同一内容再送、認可・共有・BEST判定は従来のAPIで処理する。DB・migration・環境変数・依存の追加はない。

## 送受信

- 対象は `PATCH /api/sessions/{id}` のリクエスト本文。通常のJSONも引き続き受け付ける。
- UTF-8で1,024バイト以上のJSONをブラウザ標準の `CompressionStream("gzip")` で非同期圧縮し、短くなった場合だけ `Content-Encoding: gzip` で送る。Content-Typeはapplication/json。
- 圧縮非対応、圧縮失敗、サイズが減らない場合は元のJSONを送る。15秒の送信期限を圧縮・送信・互換再送で共用し、中断を通常送信に置き換えない。
- 旧APIはgzipをJSONとして読めず、保存前に400を返すことを現在のFastAPIでも検証する。圧縮送信に対する400または415だけ、同じ本文・revisionで通常形式へ1度戻す。同じ保存キューが存続する間は以降も通常形式を使う。通常送信の400、認証失敗、409競合、413、422、サーバー障害、通信失敗はこの互換再送の対象外。
- 新APIはgzip単体のみ対応。圧縮状態・展開結果をそれぞれ128KiBに制限し、ストリーム受信中に上限を確認する。最大20種目×30セット・60文字の種目名・重量/回数の上限を含む本文が収まることを検証する。通常JSONの既存制約は変更しない。
- 展開上限超過は413、破損・途中切断・CRC不一致・連結gzip・末尾データは400、別の圧縮方式は415。入力検証と業務処理へ渡す前に拒否する。認証・認可は既存の依存処理を通る。
- 更新はAPI先行を推奨するが、旧画面→新API、新画面→旧APIの両方で保存できる。転送経路がgzipを拒否した場合も400/415なら通常形式へ戻る。それ以外の通信失敗は既存キューが端末に保持し再送する。

FastAPIの[カスタムRequest/APIRoute](https://fastapi.tiangolo.com/how-to/custom-request-and-route/)の仕組みを用い、圧縮展開をHTTP層に限定する。無制限の一括展開は使わない。

## ローカル比較

Bun 1.3.9、1回ウォームアップ＋5回の中央値。1種目30セットまで、日本語の種目名、変化する重量・回数を使い、各セット追加後の全状態に加え、先頭セットの編集・末尾セットの取消も送る。すべての本文が展開後に元JSONと完全一致することを確認する。

| 累計セット数 | 送信回数 | 従来の本文合計 | 変更後の本文合計 | 削減 | 1送信あたりの準備時間 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 30 | 32 | 15,471 B | 15,471 B | 0% | 0.006 ms |
| 150 | 152 | 312,462 B | 67,530 B | 78.4% | 0.476 ms |
| 600 | 602 | 4,780,340 B | 450,678 B | 90.6% | 0.542 ms |

```sh
cd frontend
bun scripts/benchmark-session-transfer.ts
```

これはHTTP本文のバイト数とホスト環境の圧縮準備時間。30セットの例は各本文が1KiB未満のため圧縮しない。HTTPヘッダ、レスポンス、DB処理、実回線・実機の待ち時間は測定していない。送信回数も減らないため、小さい記録やAPI処理時間が支配的な場合の高速化は主張しない。

端末保存量の削減は独立したPR #127で扱う。今回の変更はそのキュー形式に依存しない。実機・公開環境の通信時間計測と他の高速化は #11/#77 で継続する。

## 検証

- API: 通常/圧縮混在での再送、revision競合、追加/取消、グループ共有と他人の保存拒否、最大入力・不正入力。
- 展開: 小さい受信チャンク、上限丁度と超過、本文の再読取、途中切断・CRC不一致・末尾/連結データ・未対応方式。
- フロント: サイズ判定、非対応/失敗/中断、旧API再送の対象と回数、認証/競合/通信失敗の伝播。
- ブラウザ: Next.jsの転送を通る実API保存と応答消失時の再送・再開、旧API・圧縮非対応の保存。

実行結果はprogress.mdとPRに記録する。
