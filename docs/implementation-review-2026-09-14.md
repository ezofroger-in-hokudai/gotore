2026-09-14、ユーザーの「実装前に、今実装すべきものを洗い出したい」という依頼に基づく候補一覧。棚卸し時点ではアプリコードを変更していない。その後、ユーザーがIssue化と継続実装を承認した。着手順と追跡先は[週次計画 #149](https://github.com/ezofroger-in-hokudai/gotore/issues/149)へ記録し、まず既存の記録修正PR #115の最新main統合と種目管理 #148を進める。

## アプリ全体で検討する候補

ユーザーから分類以外も検討したいと追加指定があったため、分類を一分野として扱い、利用の流れ全体で比較する。以下は選定時の比較表。実装順と各機能の受け入れ条件は週次計画と各Issueで管理する。

| 分野 | 何をできるようにするか | 現状との差分・判断点 | 優先度案 |
| --- | --- | --- | --- |
| 記録の安定性 | 保存中も次の入力を続け、入力が巻き戻らない。前の種目へ戻り、未保存メモも失わない | PR #115に修正あり。新規開発より競合解消・現在の画面との統合を優先 | 最優先 |
| 体感速度 | 開く・種目追加・保存・履歴復帰の待ちを減らす | 既存のキャッシュ・差分保存・圧縮は活用済み。残る待ちを操作別に計測し、成功応答の即時反映や不要な再取得から改善 | 高 |
| トレーニングの準備 | 前回や「いつものメニュー」から種目を呼び出し、今日の重量/回数を直して記録する | 前回初期値とBESTは既存。コピーを実績の複製ではなく入力補助にするかを#75で決める。名前付きメニューは#17 | 高・方式の合意が必要 |
| 振り返り | 直近の記録をすぐ見つけ、同じ種目の前回との差を確認する | 直近履歴/分析整理はPR #117/#119。グラフや最高重量/RMの強調自体は既存。前回との差をどこに出すかを画面で確認 | 高 |
| 仲間との共有 | ホームで1種目だけでなく、その日の取り組み全体が伝わる | #104。まずは「胸・肩 / 4種目・12セット」のような既に共有する事実の短い要約を提案。AI生成や私的メモの共有は不要 | 高・表示案を比較 |
| 仲間からの反応 | 記録へ軽く反応でき、本人も見てもらえたことが分かる | #12。初版は少数のスタンプ、取消可否・共有グループをまたぐ扱いを決める。Pushは別 | 中 |

| 休憩の補助 | 時計アプリへ移らず休憩時間を確認する | #81。記録ボタンを押し出さない小さな表示。手動/セット保存時の開始を選ぶ。背景通知の保証は別 | 任意・必要性を確認 |
| 失敗からの復旧 | 通信競合した記録を控え直さずに退避・比較できる | #76。自動で上書き/マージせず、どちらの内容を使うかを利用者が選ぶ | 発生頻度次第・データ保護上は重要 |
| 種目の管理 | トレーニング開始前に候補を整理し、探す・追加・分類変更を短くする | #148。詳細は次表。お気に入り/一括操作は別に必要性を確認 | 高 |

おすすめの初回選定は「記録の安定性・体感速度」を土台にし、「種目管理」と「ホームの取り組み要約」から使いやすさを改善すること。コピー/いつものメニューは履歴を実績として誤って追加しない動作を先に決めたい。全候補を一括実装する計画ではない。

## 種目管理の内訳

| 候補 | 現状・困りごと | 変更後の操作案 | 優先度案 |
| --- | --- | --- | --- |
| 1. 記録を始めずに種目を整理 | v2の管理入口は開始後の種目選択/入力画面。旧記録編集にも管理部品があるが、日常の整理の入口には向かない | 設定などから「種目」を直接開く。セッションや記録を作らずに整理する | 高 |
| 2. 管理一覧の検索・部位絞り込み | 種目選択にはあるが管理一覧にはなく、全候補から対象を探す | 名前＋8部位で絞り込み、「その他」の分類を直せる。主/補に一致させ、取得済み候補で即切替 | 高 |
| 3. 追加・編集・削除の配置 | 追加フォームが常に先頭。一覧は名前/部位/編集/削除が並び、削除確認は一覧の下 | 一覧を先に見せ、追加時にフォームを開く。削除確認は対象の近くに置き、履歴が残ることを示す | 高 |
| 4. 整理結果をすぐ表示 | 追加/部位変更の応答を一覧へ使わず、再GET後に表示。成功後に再取得だけ失敗すると更新前の一覧が残る | 成功応答を一覧へ反映してから必要な更新を背景で行う。画面間の候補/分類の整合性と失敗時の入力保持を維持 | 高 |
| 5. よく使う種目を上へ | 手動の並べ替えやお気に入りがない | お気に入りを上に集める、または手動で並べる。両方を一度に作る必要はない | 中・方式を選ぶ |
| 6. 複数種目の部位をまとめて変更 | 部位の編集は1種目ずつ | 複数選択→主な部位を指定。補助部位の保持/削除、途中失敗・競合時の扱いを先に決める | 中・頻度次第 |
| 7. 名前の変更・重複整理 | 現状のPATCHは分類だけ。同名以外の表記揺れを自動統合しない | 候補名だけ変えるか、過去の履歴・最高記録も引き継ぐかを決める | 保留・データ設計が必要 |
| 8. いつもの種目セット | 複数種目を名前付きメニューとして呼び出せない（#17） | 「胸の日」等から種目候補をまとめて開く。実施前のセットを実績として保存しない | 後回し候補 |

種目管理を採用する場合は、まず1〜4を小さな一組として検討するのがおすすめ。5〜8は利用頻度と必要性を確認し、便利そうという理由だけで同時に追加しない。

検索・分類・配置の候補は[#148](https://github.com/ezofroger-in-hokudai/gotore/issues/148)へ記録したが、ユーザーの追加指示で未着手の候補に戻している。1/4などの範囲追加は採用時に受け入れ条件へ反映する。

## 種目整理とは別に判断する残課題

- **記録コピー（#75）**: 現行v2では確認後にコピーしたセットを保存・共有する。旧仕様の「修正してから保存」と異なるため、今日の入力候補として呼び出すのか、記録の複製なのかを決めたい。
- **通信競合からの復旧（#76）**: 端末側データは保持するが、復旧は手で控えて破棄/再読込する形。自動統合ではなく、退避・比較・再利用のどこまで必要かを確認する。
- **グループ削除（#31）**: 名前変更は既存機能。グループ自体の削除は未提供。削除後に本人履歴/共有リンクをどう扱うかを決める。
- **ホームの一言（#104）**: 種目1つだけでは全体が伝わりにくいという依頼の候補。種目数・セット数などの事実から短く示す案は検討できるが、今回の種目整理とは分ける。
- **実機の操作感（#23/#65/#110）**: iPhoneのホーム画面起動、キーボード表示中、文字拡大等。ブラウザ上の成功と区別する。
