# SCORE初版の実装仕様（#99）

2026-09-12にユーザーが [score.md](score.md) の仮案を採用した。算式・基準回・未評価の扱いは同書を適用し、元の設計案は経緯として保持する。

## 採用した方針

- 直近30日、同じ種目構成の最大総負荷の1回をI/V共通の基準にする。前日までの確定記録だけを参照する。
- Cは対象日を含む最大28日。観測日数は初回実施日と対象日の両端を含む。初回実施日は観測開始メタデータとして保持する。
- 基本配点C/I/V/Gは30/20/40/10。必要な項目が未評価なら総合点を出さず、内訳と不足理由を表示する。
- 個人目標は「入力 → AIが2〜4条件を提案 → 本人が確認・修正して保存」。AIが追加条件を勝手に確定しない。
- 開始時の目標バージョンを固定し、変更した目標は次の開始から使う。過去スコアは目標変更で再計算しない。
- 終了後は結果画面へ進み、記録の要約と数値の内訳を先に表示する。LLMの判定・一言コメントは別の通信で生成し、後から反映する。
- 結果はDBに保存し、ホーム・履歴・共有詳細の閲覧でLLMを呼ばない。本人目標・評価コメント・メモは自動共有しない。
- 個人表示には基本配点、グループ表示にはそのグループの配点を使う。週月SCOREランキングの集約方法は未確定のため、既存の量・強度のランキングとは区別する。

## 標準目標とLLM

- ユーザー確認済みの標準条件は「筋トレに当たる種目への取り組み」「目標の指定に沿った種目・セット配分」の2件。標準目標は配分を指定しないため自由な配分を認める。自重・軽い負荷・新種目を理由に減点しない。一般目標なので高得点になりやすく、身体への適性は断定しない。
- ユーザーは安さ・速さを優先。追加指定により既定をOpenAI GPT-5 nanoへ変更し、`reasoning.effort=minimal` と短い構造化出力を使う。環境変数で指定し、結果には実際のモデル識別子を保存する。採用モデルの実測速度・判定品質は代表例で検証する。

## 検証方針

算式88点・95%境界・区間境界・種目構成・自重/高回数・未評価をドメインテスト、開始/終了/目標変更/訂正/削除/認可を専用DB統合テストで確認する。LLMの重複要求・失敗・不正な出力、目標変更前の履歴混入、個人情報の共有漏れを検証する。画面はLLM遅延中の操作、再訪・切り替え、320/390/430pxで確認する。

## LLMの調査根拠

2026-09-12確認。ユーザーの「最も安くて早い」追加指定を受け、通常のテキスト生成の単価を優先してGPT-5 nanoを採用する。Responses APIとStructured Outputsに対応し、100万トークンあたり入力$0.05・キャッシュ入力$0.005・出力$0.40。従来のGPT-5.6 Luna（入力$0.20・出力$1.20）に対して通常入力は1/4、出力は1/3の単価。

GPT-5 nanoは推論を完全には無効化できないため、最小の`minimal`を指定する。推論トークンも出力の費用と1,200トークン上限に含まれる。GPT-4.1 nanoは推論段階なしで低遅延だが入力単価は$0.10。このため「最安の単価」と「実際の最速」を同時に保証するものではない。総費用・応答時間・品質はキー設定後に #100 で測定する。

新規採点と目標提案で新モデルを使う。既存の採点済み結果は再生成せず、以前のLunaへ固定済みの失敗再試行は`none`を維持する。Vercelに`SCORE_MODEL`を明示している場合は`gpt-5-nano`へ変更して再デプロイする。

## 保存・通信と再採点

- 追加migrationは `20260912010000_workout_scores.sql`。目標版、開始時の固定、初回観測日、採点根拠・結果、グループ配点版、日別利用回数を保存する。全6テーブルでRLSを有効にし、ブラウザから直接操作させない。公開DBの適用はリリース担当者がAPI更新前に行う。既存記録から初回観測日だけを移し、過去記録を一括採点しない。導入前から進行中の記録も、開始時の目標がないため対象外。
- 終了のトランザクションでC/I/V・開始時目標・元の比較対象・判定入力を保存し、画面へ返す。画面遷移後に本人の `POST /workouts/{id}/score/evaluate` を呼ぶ。外部APIを待つ間はDB接続と記録ロックを解放する。
- 採点は記録ごとに60秒の実行権を取得する。同時要求は生成せず保存済み状態を返す。完了後はGET・再送・複数グループの閲覧でも生成しない。通信失敗後の明示再試行は固定済み入力・プロンプト・モデルを再利用する。応答不明の障害時に提供元側の課金まで厳密に一回とする保証はない。
- ユーザー承認により、記録訂正はその記録だけ再採点する。開始時目標と最初の比較対象を保持し、訂正後の実績・実施日でC/I/Vと判定入力を更新する。種目構成が元の比較対象と異なる場合I/Vは未評価。比較対象の後日の編集・削除は保存済み根拠を変えない。他の記録へ変更を波及させない。保存の再送・同じ内容での更新は再採点を増やさない。旧revisionのAI応答は破棄する。
- 目標版・記録revision・算式版・プロンプト版・モデル識別子を保持する。削除時は採点も削除する。配点変更はオーナーのみ、次の月曜日から適用。記録実施日に有効な版を選び、Gの再生成はしない。

## 閲覧速度と表示

- 開始・セット保存・heartbeat・通常フィードのDB往復上限は従来の7/4/2/4を維持。終了は従来3往復に採点根拠の一括取得と保存を加え5往復。履歴・フィードのスコアは一括取得し、大きな判定入力を一覧に返さない。
- 設定用目標はホーム表示後の空き時間に先読み。スコア詳細はタップ前のポインター・フォーカス時にも先読みする。共有詳細キャッシュは採点結果の更新でも無効化する。
- 終了後の採点要求はワークスペース内で保持し、ホーム・履歴へ切り替えても続行する。保持する結果は最大10件。ログアウトでは要求とキャッシュを破棄する。別端末で採点中なら結果だけを短時間ポーリングする。
- 初回・比較対象なし・評価に必要な観測期間不足では総合点を補わず内訳を表示する。AI待機・失敗でも記録は保存済み。再試行は本人が結果画面または履歴詳細から実行する。

## AI入力と利用上限

- OpenAIへ送るのは目標本文・確認済み条件・今回と同じ目標版の直近30日の種目別要約。ユーザーID・グループ・個人メモ・基準回の識別子を送らない。任意入力内に本人が書いた個人情報は含まれるため、目標には評価に必要な内容を記入する。
- 履歴は最新60回まで、JSON入力は履歴追加時に15,000文字までに制限。切り詰めた場合、複数日を必要とする条件は未評価にする。出力上限1,200トークン、通信タイムアウト15秒。`store: false` を指定するが、提供元の不正利用監視等の保持条件は公式資料に従う。
- 既定の呼び出し上限は本人ごと・JST日単位で採点30回、目標提案10回。失敗・訂正後の生成も数える。上限超過では新しいAI要求だけを拒否し、記録保存・閲覧・既存の内訳を利用できる。`SCORE_DAILY_LIMIT` / `GOAL_PROPOSAL_DAILY_LIMIT` で1〜1000に変更可能。金額上限ではないため提供元側の予算も設定する。
- 秘密キーは `backend/.env` またはAPI実行環境の `OPENAI_API_KEY` のみに設定し、変更後にAPIを再起動する。未設定の場合はAI評価・新規提案が利用できず、記録と数値内訳は保存する。実モデルによる速度・判定品質の評価は未実施で、[後続 #100](https://github.com/ezofroger-in-hokudai/gotore/issues/100) で追跡する。テスト画像のコメントとスコアは固定した検証データ。
