# デザイン判断メモ

完成までローカルで更新する設計メモ。実装仕様の正本をただちに上書きしない。

## 2026-09-22: メモの役割と記録画面の情報密度

### 決定

- 種目メモは、内容がある時だけ種目名の下へ薄い「✎ メモ」と本文1行で表示する。押すと編集でき、空なら場所を取らない。
- 記録中に残すトレーニング全体のメモは、数値入力付近の紙とペンのアイコンから開く。画面上で「今回」などの曖昧な言葉は使わない。
- 記録中の種目名を押した詳細にも、種目メモを編集する入口を置く。
- 記録画面は種目名、保存済みセット、数値入力、次の操作を主役にする。説明文、常時表示のメモ枠、装飾だけの余白を増やさない。

### 言葉のルール

- 内部のデータ区分や実装都合の言葉を画面に出さない。
- 「今回」「状態」「同期済み」など、単独で意味が決まらない言葉は通常画面で使わない。
- 文字を置く場合は、対象と操作が一度で分かる短い言葉にする。例: 「メモ」「まだ続ける」「今日のトレーニング終了」。
- 押せるものは文字だけで置かない。枠、矢印、背景、アイコン、48px以上の操作領域で操作可能と分かる形にする。

### 守ること

- 種目メモとトレーニング全体のメモは保存対象を混同しない。
- メモの下書き、保存失敗時の復旧、本人限定の扱いは維持する。
- 通常時の保存・送信・同期状態は画面に出さない。利用者の対応が必要で、端末の保存でも守れない場合だけ知らせる。

### 次に見本で決めること

1. 種目選択の行でメモをどう見せるか。
2. 記録中の紙とペンの入口を、SET見出しのどこへ置くか。
3. 種目名の詳細から種目メモを開く形。
4. 文字・余白・ボタンの密度を、320px幅で保つ形。

## 2026-09-22: 数値入力とライブ感

この節の方針は、ユーザー確認により採用済みとする。実アプリへの反映は、他の優先画面のデザイン確定後にまとめて行う。

### 決定

- 重量ホイールは0.5kg単位で増減できることを必須にする。2.5kg固定の操作にはしない。
- 数字を押して直接入力できることを、画面上の大きな説明や追加ボタンで無理に示さない。ホイールで0.5kg単位まで完結することを優先する。
- 記録中には、仲間のスタンプ、セット保存、自己ベストを短いライブ通知として出す。
- 通知は「名前 + アイコン + 結果」の順に短くし、「〜が」「〜しました」などの説明は省く。
- 通知は数値入力やセット一覧を押し下げない。一度に主張するのは1件だけとし、複数件は後続の検討でまとめ方を決める。

### 比較中の案

[記録画面のライブ通知3案](training-options/index.html)を作成した。

- A: ヘッダー直下の固定位置に1件。
- B: セット一覧に一時的に重ねる。
- C: 小さいライブ列に仲間と直近の結果をまとめる。

どの案も通常の保存・送信状態は表示しない。これは仲間の行動だけを知らせるための表示である。

### 採用する方向

- ライブ通知はBを軸にする。セット一覧へ一時的に重ね、表示のために入力欄や一覧の位置を動かさない。
- 通知は名前と結果が分かる程度まで書く。例: 「みおが自己ベスト達成　🔥」。通知が幅に収まらない場合は、意味の途中で切れない短い定型へ置き換える。
- 記録中のメモ入口は鉛筆だけにせず、鉛筆と「メモ」を併記する。数値入力の横の入口を基準にする。
- 記録中のメモ入口は数値入力の横だけに置く。ヘッダーには同じ入口を置かず、種目メモは種目選択画面でのみ扱う。
- スタンプはセット保存や自己ベストの通知と分ける。名前とスタンプだけの小さなバッジを、セット一覧に一時的に重ねてふわっと表示する。
- スタンプは同じ相手・同じ記録に対しても回数制限を設けない。連続したスタンプも件数へまとめず、一つずつ短い間隔でふわっと表示する。画面に同時表示するのは最大3件にし、以降は順番に表示して送られた分を省略しない。
- 次のセットの入力欄は最初から開く。利用者が必要なときだけ矢印でホイールをしまえるようにし、毎セットで開く操作を求めない。
- 保存済みセットは行全体を押して編集できる。押した記録の値を同じ入力欄へ読み込み、見出しを「SET 1 を編集」、主操作を「更新する」に切り替える。編集用の別画面やモーダルは開かない。
- スタンプのバッジは操作を受け取らず、下にあるセット行のタップを妨げない。
